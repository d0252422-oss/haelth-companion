# Health Data Layer v2 Schema Draft

Date: 2026-08-25  
Status: **DRAFT ONLY — NOT APPROVED FOR PRODUCTION**

Executable-looking detail is intentionally isolated in `supabase/drafts/health_data_layer_v2.sql`. That file contains an abort guard and was not executed.

## Naming and type conventions

- Database identifiers: `snake_case`.
- Primary keys: UUID generated by `gen_random_uuid()` unless an existing composite key is retained.
- User ownership: `user_id uuid` referencing `public.users(id)`.
- Event timestamps: `timestamptz`; reporting boundary: `local_date date` plus user timezone.
- Quantities: `numeric`; counters/durations: integer/bigint with non-negative checks.
- Soft deletion only where a current mutable fact needs it; immutable ingestion events are not soft-deleted.
- `data_quality jsonb` stores flags/version metadata, not the primary measurement.
- Source types use `health_source_type`: `MANUAL`, `LEGACY_SHEET`, `HEALTH_CONNECT`, `WEARABLE`, `AI_DERIVED`, `IMPORT`, `OTHER_APP`, plus `SYSTEM_DERIVED` for deterministic summaries/scores.

## Core column contracts

### `user_identities`

`id`, canonical `user_id`, provider (`GOOGLE`, `LINE`, `LEGACY_SHEET`), SHA-256 `provider_subject_hash`, optional normalized-email hash, link status, verification timestamp and non-secret metadata. Unique `(provider, provider_subject_hash)` prevents one external identity from owning two users. One user may own multiple verified links. Email is a discovery hint only; any conflicting subject mapping is quarantined and never auto-merged. The table is RLS-enabled but has no authenticated policies or grants; only the trusted service workflow can read or mutate it.

### `user_devices`

`id`, `user_id`, `source_system`, `source_device_id`, `manufacturer`, `model`, `device_category`, `capabilities`, `accuracy_profile`, `first_seen_at`, `last_seen_at`, `status`, `confidence`, timestamps. Unique `(user_id, source_system, source_device_id)`. Authenticated users may read their registry but cannot directly write source/confidence/accuracy fields; trusted ingestion or a future validated declaration workflow owns mutations.

### `ingestion_events`

`id`, `user_id`, `source_type`, `source_system`, optional `source_device_id`, `idempotency_key`, `received_at`, optional source interval, `status`, accepted/rejected counts, `payload_hash`, schema version, sanitized metadata, error code and timestamps. Unique `(user_id, source_system, idempotency_key)`. Identity, ownership, source key, payload hash and schema version are immutable after insert; service workers may update only bounded lifecycle fields and cannot delete the event. A production rollback preserves the event as `ROLLED_BACK`. Every M2 backfill batch has its own `LEGACY_SHEET` event; every row loaded by that batch must carry the event's `ingestion_id`.

No plaintext authorization header, OAuth token, API key, sync secret or unrestricted raw request body is stored.

### `health_samples`

Composite identity `(id, observed_at)`, provenance contract, controlled `metric_type`, one required numeric value plus `unit`, `local_date`, `record_layer`, and mandatory `source_fingerprint`. Arbitrary structured domain values are prohibited in this high-rate table; versioned quality flags may live in `data_quality`, while complex observations require a domain table. The table is monthly range-partitioned by UTC `observed_at`; raw rows are immutable and have no soft-delete column. Dedup uniqueness includes the partition key and mandatory fingerprint. A default partition is monitored quarantine only.

### Domain facts

- `body_measurements`: existing body metrics plus provenance fields.
- `activity_daily`: unique `(user_id, local_date, source_system, source_device_id)` with non-negative steps/calories/minutes.
- `workouts`: provenance and session interval.
- `workout_exercises`: direct `user_id`, `workout_id`, `exercise_key/name`, ordinal, with an owner/workout composite candidate key.
- `workout_sets`: direct `user_id`, optional `workout_exercise_id`, ordinal/weight/reps/duration/distance. A composite `(workout_exercise_id, workout_id, user_id)` FK prevents cross-workout and cross-owner attachment; direct-user RLS waits for backfill, validation and `NOT NULL` enforcement.
- `sleep_sessions`: provenance, sleep interval and stage evidence.
- `daily_checkins`: unique `(user_id, local_date, source_system)` with bounded subjective scores.

### Daily summaries

Every summary has:

- `user_id`, date primary key
- provenance fields (`observed_at`, `recorded_at`, `source_type=SYSTEM_DERIVED`, `source_system`, optional device/ingestion IDs, confidence)
- domain totals/metrics
- `summary_version`, `algorithm_version`
- `input_fingerprint`
- `completeness`, `data_quality`
- `source_max_updated_at`, `computed_at`, `created_at`, `updated_at`
- `is_stale`; true from atomic fact/queue mutation until a matching-watermark recomputation succeeds

`nutrition_daily_summary`, `sleep_daily_summary` and `daily_health_summary` are recomputable read models. Facts remain authoritative.

### `summary_recompute_queue`

Unique `(user_id, domain, local_date)`, with monotonically increasing source generation, source watermark, status, priority, attempt count, lease owner/expiry, leased generation, next-attempt time, last error code and timestamps. A fact-write transaction upserts this row and increments its source generation. Workers use bounded leases and compare-and-swap completion: success may clear stale state only when both the leased generation and source watermark still match. A late concurrent write therefore cannot be acknowledged by an older worker.

### Scores and AI

- `health_scores`: unique `(user_id, score_date, algorithm_version, input_fingerprint)` so recomputation retains superseded evidence instead of overwriting it; overall score, state, completeness and input fingerprint. `publication_status` separates `DRAFT`, `ACTIVE` and `SUPERSEDED`, with at most one active score per user/date; dashboard reads select only `ACTIVE`.
- `health_score_components`: direct `user_id`, score FK, domain/component, value, weight, evidence refs and quality flags.
- `ai_analysis_runs`: provider/model/prompt/schema versions, status, input/output fingerprints, token/latency metadata and timestamps.
- `ai_derived_metrics`: direct `user_id`, run FK, metric/value/unit/time window/confidence, source references and quality.

Raw or canonical facts never change source type to `AI_DERIVED`. Human-approved AI suggestions create a separate canonical mutation with explicit confirmation evidence.

## Relationship design

```text
auth.users 1--1 users
users 1--* user_identities
users 1--* user_devices
users 1--* ingestion_events
user_devices 1--* ingestion_events / health facts
ingestion_events 1--* health_samples / canonical facts
users 1--* meals 1--* meal_items
users 1--* workouts 1--* workout_exercises 1--* workout_sets
users 1--* sleep_sessions
users 1--* daily domain summaries
users 1--* health_scores 1--* health_score_components
users 1--* ai_analysis_runs 1--* ai_derived_metrics
```

Hot child tables carry `user_id`. Composite uniqueness/FKs ensure child `user_id` matches parent ownership, avoiding slow parent-join RLS without sacrificing integrity.

## RLS matrix

| Table class | SELECT | INSERT | UPDATE | DELETE |
|---|---|---|---|---|
| User-owned mutable | Owner | Owner | Owner, with owner check on result | Owner |
| User-owned immutable ingestion | Owner metadata if product requires it; otherwise service | Service/client scope | Service state transition only | No client delete |
| Derived summaries/scores | Owner | Service | Service | No client delete |
| Shared lookup | Authenticated read | Service/admin | Service/admin | Service/admin |
| Internal quality/worker state | Owner bounded read or service | Service | Service | Service |

All owner predicates use `(select auth.uid())`. UPDATE policies require both SELECT visibility and `WITH CHECK`. Grants are explicit and reviewed separately from RLS.

## Dashboard RPC draft contract

`get_dashboard_v2(p_local_date date)`:

- authenticated only
- SECURITY INVOKER, `STABLE`, `set search_path = ''`
- derives caller from `(select auth.uid())`; does not accept arbitrary `user_id`
- bounded lookups from daily summaries, latest body measurement and current score; activity is supplied by the selected activity projection in `daily_health_summary`
- returns a versioned JSON/result type
- returns explicit freshness (`is_stale`, computation timestamp and source watermark/version)
- never invokes recomputation on the read path

## Compatibility surfaces

- Existing Apps Script remains primary during M0–M5.
- Compatibility adapters preserve existing Web App/GPT field names while reading canonical v2.
- `heart_rate_samples` and legacy daily summary remain available until consumer inventory and parity pass.
- No v1 table is dropped by the draft.

## Assumptions requiring review

1. `public.users.id` remains equal to `auth.users.id` for every migrated account after deterministic external-identity validation; unresolved legacy-only rows remain quarantined rather than receiving a guessed auth identity.
2. Source timestamps can be normalized without losing the original source time/zone evidence.
3. Health Connect can supply stable record IDs or deterministic hashes.
4. Food embeddings remain useful enough to retain pgvector.
5. Dashboard consumers accept a versioned compatibility adapter rather than direct table access.
6. Raw sensor retention and expected daily volume remain to be approved.
